### 1.1 文档目的

本文将系统落地方案转换为可设计、可开发、可测试和可验收的需求基线，用于：

- 统一产品、设计、研发、测试、安全、合约和运营团队对产品范围的理解。
- 明确用户角色、业务流程、功能需求、业务规则、状态与权限边界。
- 为接口、数据模型、智能合约、测试用例和阶段验收提供可追踪依据。
- 将未决参数与既定需求分离，避免在开发中隐式作出高风险业务决策。

### 1.2 需求措辞

- “必须”：上线或对应阶段验收的强制要求。
- “应”：默认需要满足，若不满足必须形成书面评审结论。
- “可以”：可选能力，不构成当前阶段验收阻塞项。
- 优先级采用 `P0/P1/P2`：`P0` 为闭环或安全底线，`P1` 为完整运营能力，`P2` 为生产与持续优化能力。

## 2. 产品概述

### 2.1 产品定位

平台连接任务发布者与专业 AI Agent。任务发布者使用以太坊兼容钱包登录、发布任务并单边托管任务资金；平台从合格 Agent 中推荐最多 3 个候选，候选先交付付费且受限的概览，发布者再选择一个 Agent 完成正式交付。正式交付默认包含 V1 至 V3，超范围或继续优化通过变更单扩展至 V4、V5。正常验收后链上结算；符合条件的争议进入平台证据、初裁、一次独立复核和链上分配流程。

### 2.2 核心价值

- 对任务发布者：先比较概览再选择 Agent，任务资金链上托管，过程、版本和费用可追踪。
- 对 Agent 提供者：按统一协议接入并获得公平曝光，有效概览可获费，接单无需缴纳任务级履约金。
- 对平台：通过可解释匹配、不可变账务、链上资金状态和证据体系建立可信交易闭环。

### 2.3 产品目标

| 编号 | 目标 | 验收方向 |
| --- | --- | --- |
| OBJ-01 | 打通 Agent 注册、匹配、概览、选择、正式交付、修改与结算闭环 | 真实 Agent 在测试链完成端到端任务 |
| OBJ-02 | 实现发布者单边托管、Agent 零任务级履约金 | Agent 未入金仍可被选中、交付并收款 |
| OBJ-03 | 提供质量与公平兼顾的可解释推荐 | 硬过滤、混合召回、100 分评分、五维信誉和 FairShuffle 可审计 |
| OBJ-04 | 隔离候选、正式任务、变更单、争议与外部成本 | 每笔资金有独立账户、流水、状态与处分条件 |
| OBJ-05 | 控制无限修改与范围漂移 | 冻结任务范围，V1–V3 套餐化，V4/V5 依赖变更单，拒绝 V6 |
| OBJ-06 | 建立可执行的平台争议处置机制 | 资格、冻结、证据、初裁、一次复核和逐账分配完整闭环 |
| OBJ-07 | 保证链上链下和异步执行一致性 | 重试、重放、乱序和并发不会造成重复执行、计费或出金 |

### 2.4 成功指标

业务目标值尚未在来源方案中冻结。产品负责人需在阶段 0 确认至少以下指标及目标值：

- Agent 注册协议校验通过率、健康率。
- 合格任务的候选覆盖率、概览有效率、补位率和选择率。
- 正式任务按时交付率、V1/V2/V3 验收分布、范围变更率。
- 退款率、争议申请率、初裁与复核及时率。
- 账务日对账差异数、重复计费或重复出金事故数。
- 核心 API 可用性、任务端到端成功率和资金类严重事故数。

## 3. 范围

### 3.1 本期完整范围

- 钱包签名认证、会话与多角色权限。
- Agent 注册、定价、能力、凭证、健康、容量和执行记录。
- 任务创建、规格与验收标准冻结、预算授权和状态管理。
- 硬过滤、混合召回、规则评分、五维信誉、模型有限调整与公平洗牌。
- 最多 3 个候选 Agent 的并行受限概览、质量校验、费用结算和补位。
- Agent 选择、选中概览一次抵扣、正式预算净额锁定。
- 正式版 V1–V3、结构化修改、版本差异和评审；变更单驱动 V4/V5。
- 四个业务子账、外部成本 allocation、不可变双重账本、退款与对账。
- 验收结算、Agent 收益账户、立即提现与自愿生息。
- 平台争议申请、反请求、证据、初裁、一次复核、和解和逐账链上分配。
- 管理后台、审计、监控、告警、消息重试与死信处理。
- 以太坊测试链完整闭环；通过安全与治理准入后进行主网受控试运行。

### 3.2 非目标

- 法币、支付宝或微信支付。
- 原生 iOS 或 Android 应用。
- 面向全球公众的无差别、规模化主网商业运营。
- 在智能合约中存储任务正文、交付物、Agent API 凭证等敏感或大体积数据。
- 由平台管理员代替用户签署普通钱包资金交易。
- 向 Agent 收取任务级履约金、保证金或押金。
- 当前版本不包含多 Agent 工作流、任务拆分和里程碑聚合结算；此类能力属于后续演进。

## 4. 核心原则与业务底线

| 编号 | 原则 |
| --- | --- |
| BR-01 | 正式任务本金只由任务发布者支付；Agent 接单、执行和交付不缴任务级履约金。 |
| BR-02 | 智能合约是托管资金状态的最终真相源；PostgreSQL 是链下业务数据的真相源；Redis 仅保存可重建数据。 |
| BR-03 | `DiscoveryPool`、`FormalEscrow`、`ChangeOrderEscrow`、`DisputeFeePool` 必须独立记账和处分。 |
| BR-04 | 外部成本必须以所属业务子账下的独立 allocation 授权、捕获、释放和退款，不得复用正式本金余额。 |
| BR-05 | 已结算的有效概览费、其他任务收入和 Agent 收益账户不得被当前任务争议追索或罚没。 |
| BR-06 | 原账务流水、任务规格、验收标准、匹配快照、正式版本和证据不得覆盖；更正只能通过新版本或冲正流水。 |
| BR-07 | 所有消息消费者、链上事件消费者和关键写接口必须幂等。 |
| BR-08 | 前端和 BFF 的权限判断不替代 Engine 的角色、资源归属、业务状态与幂等校验。 |
| BR-09 | 浏览器请求必须经 BFF 到 Engine；浏览器不得直接访问 Engine 内部接口。 |
| BR-10 | 用户私钥、Agent 凭证、JWT、API Key 和无需长期保存的签名不得以明文存储或记录。 |

## 5. 用户角色与权限

### 5.1 角色定义

| 角色 | 职责 |
| --- | --- |
| `TASK_PUBLISHER` | 创建任务、托管资金、查看候选、选择 Agent、提交反馈、验收、退款或发起合格争议 |
| `AGENT_PROVIDER` | 创建和维护 Agent、提交概览与正式交付、处理修改与变更单、查看收入和提现 |
| `ADMIN` | 用户与 Agent 治理、异常任务、对账、死信、审计和系统配置；不得代签用户交易或读取凭证明文 |
| `DISPUTE_REVIEWER` | 处理被分配且无利益冲突的初裁案件 |
| `DECISION_REVIEWER` | 处理被分配的复核案件；不得参与同案初裁 |

同一普通用户可以同时拥有任务发布者与 Agent 提供者角色，但关联账户不得匹配自己的任务、领取自己的概览补贴或处理自己的争议案件。

### 5.2 权限需求

| 编号 | 优先级 | 需求与验收口径 |
| --- | --- | --- |
| AUTH-01 | P0 | 普通用户必须通过服务端一次性 nonce 和钱包签名登录；签名内容必须绑定域名、链 ID、nonce、签发时间和用途。重复、过期或跨环境签名必须失败。 |
| AUTH-02 | P0 | 每个受保护接口必须校验角色、资源所有者、当前领域状态和幂等性；替换资源 ID 不得读取或修改他人资源。 |
| AUTH-03 | P0 | Agent 提供者只能维护自己的 Agent；发布者只能操作自己的任务；候选期 Agent 只能读取脱敏简报。 |
| AUTH-04 | P0 | Agent 调用凭证必须加密保存，只允许所有者更新且不得回显明文；管理员和裁决人员均不得读取明文。 |
| AUTH-05 | P1 | 管理员、初裁员和复核员使用独立受控入口与强化认证；高风险操作必须记录原因和不可静默删除的审计日志。 |
| AUTH-06 | P0 | 初裁、复核、资格签发、暂停和升级权限必须分离；利益冲突账户不得接案。 |
| AUTH-07 | P0 | 管理员不得代替用户创建钱包签名、托管、选择 Agent 或普通验收，不得通过后台直接改写链上资金决定。 |

## 6. 核心用户旅程

### 6.1 Agent 发布旅程

1. Agent 提供者连接钱包并完成签名登录。
2. 填写 Agent 基础资料、分类、能力、标签、定价、语言、时限和容量。
3. 设置调用地址并写入安全凭证。
4. 平台完成字段、价格、协议、连通性和健康检查。
5. 通过校验后 Agent 进入 `ACTIVE`，参与匹配并持续接受健康与容量检查。

### 6.2 任务交易主旅程

1. 发布者登录，创建任务规格、输入清单、验收标准、预算和时限。
2. 发布者分别授权候选概览预算和最高正式任务预算；需要外部成本时独立授权。
3. 链上资金确认后平台匹配最多 3 个候选，并固化匹配快照。
4. 候选并行生成受限概览；有效概览按冻结价格结算，失败额度释放或受控补位。
5. 发布者从成功概览中选择一个 Agent；合约验证发布者授权与平台证明后原子完成选择、一次抵扣、正式净额锁定和差额释放。
6. Agent 提交正式 V1；发布者可以验收或提交合并的结构化修改意见，依次生成 V2、V3。
7. 超范围需求或 V4/V5 必须形成有效变更单；同一交付单元永久拒绝 V6。
8. 发布者验收后链上结算；Agent 选择立即提现或明确授权后继续生息。
9. 达到资格且仍不满意时，发布者可以发起平台争议；符合独立触发条件的 Agent 也可以发起争议。

### 6.3 争议旅程

1. 后端计算并返回争议能力及不可执行原因。
2. 申请人提交签名意图和申请费，平台生成基础证据与冻结账户根。
3. 链上冻结确认后案件进入有效争议状态，并开放主张/反请求窗口。
4. 双方可和解；未和解时完成答辩、补证与证据关闭。
5. 无利益冲突的初裁组作出初次决定。
6. 当事人可在 72 小时内申请唯一一次独立复核并原子支付复核费。
7. 最终决定生效后，合约逐账执行完整分配，所有冻结叶子和争议费处置完毕后案件终结。

## 7. 功能需求

### 7.1 钱包、身份与会话

| 编号 | 优先级 | 需求与验收口径 |
| --- | --- | --- |
| LOGIN-01 | P0 | 登录页必须允许用户选择“发布任务”或“上传 Agent”模式，再连接以太坊兼容钱包。 |
| LOGIN-02 | P0 | 系统必须处理未安装钱包、未连接、用户拒签、错误网络、交易失败和替换交易，并给出可恢复提示。 |
| LOGIN-03 | P0 | 登录成功后会话必须包含用户、钱包地址与角色；角色变更或用户冻结后旧会话必须失效或及时刷新。 |
| LOGIN-04 | P1 | 移动 Web 应支持响应式布局和移动钱包跳转。 |

### 7.2 Agent 管理

| 编号 | 优先级 | 需求与验收口径 |
| --- | --- | --- |
| AGENT-01 | P0 | 提供 Agent 创建、编辑、启用、停用和查看功能，字段至少包括名称、分类、标签、能力描述、语言、预计时限、并发容量、作者介绍、控制者和收款地址。 |
| AGENT-02 | P0 | Agent 必须配置概览价、正式套餐总价、额外版本价、外部成本上限和价格版本；平台固定包含 3 个正式版本、单交付单元最多 5 个。 |
| AGENT-03 | P0 | 发布价格版本时必须满足 `0 <= overview_price <= formal_package_gross_price`，数据库、匹配、选择与合约重复校验。 |
| AGENT-04 | P0 | 平台必须测试 Agent API 连通性和协议兼容性；不健康、无容量、未审核或受处罚的 Agent 不得参与匹配。 |
| AGENT-05 | P1 | Agent 提供者可以查看匹配、概览、选择、正式执行、变更单、争议、费用和结算记录。 |
| AGENT-06 | P0 | Agent 接单与执行不得产生任务级履约金入金步骤或相关账务字段。 |

### 7.3 任务创建与发布

| 编号 | 优先级 | 需求与验收口径 |
| --- | --- | --- |
| TASK-01 | P0 | 发布者可以创建草稿，填写任务描述、专家类型、语言、预算、完成时限、输入数据、允许工具、排除项、交付格式和验收标准。 |
| TASK-02 | P0 | 发布前必须生成不可覆盖的任务规格版本与内容哈希；验收标准必须有权重和冻结版本。 |
| TASK-03 | P0 | 平台必须分别展示候选概览预算、正式任务最高预算、平台费和外部成本上限，不得以单一可变余额模糊展示。 |
| TASK-04 | P0 | 资金确认前任务不得进入匹配；前端不得仅依据钱包返回结果显示“已托管”。 |
| TASK-05 | P1 | 平台应通过 `available-actions` 返回当前可执行动作和不可执行原因，前端不得自行推导关键资格。 |

### 7.4 匹配与推荐

| 编号 | 优先级 | 需求与验收口径 |
| --- | --- | --- |
| MATCH-01 | P0 | 匹配必须依次执行硬条件过滤、三路召回、去重与规则评分、模型有限调整、合格池筛选和公平洗牌。 |
| MATCH-02 | P0 | 硬过滤必须覆盖状态、审核、5 分钟健康有效期、容量、分类、协议、预算、时限、语言、风控、收款地址和向量版本。 |
| MATCH-03 | P0 | 三路召回分别为稠密语义、标签/关键词、分类/必需项精确召回，各取 Top-100，融合去重后最多 100 个进入评分。 |
| MATCH-04 | P0 | `RuleScore` 必须为 100 分制：任务匹配 60、五维信誉 25、价格与时间 10、可用性 5。 |
| MATCH-05 | P1 | CTR/LTR 仅允许在规则分基础上调整 ±5 分；模型不可用或未达上线标准时调整为 0。 |
| MATCH-06 | P0 | 合格池必须同时满足 `RuleScore >= 60`、`RankingScore >= 60`、与当前最高分差不超过 10，最多保留 20 个。候选不足 3 个时返回实际数量，不得用低质量 Agent 凑数。 |
| MATCH-07 | P0 | FairShuffle 必须采用确定性、带权、不放回抽样；最终最多 3 个，同服务商默认最多 1 个。 |
| MATCH-08 | P1 | 探索流量固定 15%；探索 Agent 只能占第三位，仍必须满足全部质量门槛。 |
| MATCH-09 | P0 | 同一 `task_id + match_revision + algorithm_version` 刷新结果必须稳定；只有有效输入变化才增加匹配修订。 |
| MATCH-10 | P0 | 每次展示必须保存任务、算法/模型/规则版本、分项得分、价格、权重、概率、位置、探索标记、排除原因和 seed 摘要。 |
| MATCH-11 | P1 | Qdrant、Embedding、模型或 Redis 故障时必须按固定策略降级并产生指标、日志与审计事件，不得绕过硬门槛。 |

### 7.5 候选概览

| 编号 | 优先级 | 需求与验收口径 |
| --- | --- | --- |
| OVERVIEW-01 | P0 | 平台从当前匹配快照中并行调用最多 3 个候选，使用统一截止时间；每个执行绑定任务规格哈希、匹配修订、候选与独立 allocation。 |
| OVERVIEW-02 | P0 | 候选仅获得脱敏简报、短期令牌、只读工具和受限额度；概览阶段禁止发邮件、下单、转账、删除数据等外部写操作。 |
| OVERVIEW-03 | P0 | 概览应包含理解摘要、方法、交付结构、关键风险、预计时限和有限示例，不得直接输出完整成品。 |
| OVERVIEW-04 | P0 | 只有通过格式、时限、安全、重复度和完整性客观校验的概览才能结算并进入可选择状态。 |
| OVERVIEW-05 | P0 | 有效概览无论是否中选均按冻结报价结算；用户主观不喜欢不是拒付理由。失败、超时、越权或无效概览不得结算。 |
| OVERVIEW-06 | P1 | 候选失败时可从原合格池确定性补位一次；责任方或平台故障不得导致用户为相同规格重复付费。 |
| OVERVIEW-07 | P0 | 任务规格或匹配修订变化后旧概览必须标记 `OBSOLETE`，不得选择或抵扣。 |

### 7.6 选择 Agent

| 编号 | 优先级 | 需求与验收口径 |
| --- | --- | --- |
| SELECT-01 | P0 | 发布者只能选择当前匹配修订中概览成功且仍健康、有正式容量的候选。 |
| SELECT-02 | P0 | 选择必须由发布者直接发起链上调用，或使用绑定任务、Agent、控制者、收款地址、概览、allocation、报价、金额、政策、链、合约、nonce 和有效期的 EIP-712 意图。 |
| SELECT-03 | P0 | 合约必须逐项比较发布者选择授权与平台概览证明的共同字段；篡改、交叉拼接、过期、重放或跨链证明必须失败。 |
| SELECT-04 | P0 | 选择必须原子消费一次性 nonce、创建唯一 assignment、应用一次概览抵扣、锁定正式净应付、释放超额预算并初始化 V1 work nonce。并发选择最多成功一次。 |
| SELECT-05 | P0 | `formal_payable = formal_package_gross_price - selected_overview_credit`；抵扣不得超过概览价或套餐总价，也不得移动或追回已结算概览费。 |
| SELECT-06 | P0 | 链上交易确认前仅允许链下预留，不得显示已完成分配；交易失败必须释放预留。 |

| FORMAL-03 | P0 | 失败、重试、重复回调、相同内容、流式分片、刷新下载和作废 assignment 不得增加版本号或重复计费。 |
| FORMAL-04 | P0 | 每次启动新工作前，发布者签名修改意图或有效变更单必须在链上递增 `work_nonce` 并作废旧结算资格。 |
| FORMAL-05 | P0 | 每个成功版本必须登记绑定任务、assignment、交付单元、范围、版本哈希、聚合版本、work nonce、Agent、期限和策略的交付证明。 |

| FORMAL-10 | P0 | V1 提前验收时，不退还套餐中未使用轮次的隐含预算。 |

## 8. 状态需求

### 8.1 链下任务主状态

```text
DRAFT → PENDING_ESCROW → ESCROWED → MATCHING
→ OVERVIEW_GENERATING → AWAITING_SELECTION → ASSIGNED
→ FORMAL_GENERATING ↔ FORMAL_REVIEW ↔ REVISION_REQUESTED
→ CHANGE_ORDER_PENDING
→ ACCEPTED → SETTLEMENT_PENDING → SETTLED
```

允许按规则进入的异常或终态包括：

```text
CANCELLED / REFUND_PENDING / REFUNDED /
DISPUTE_REQUESTED / DISPUTED / PARTIALLY_SETTLED / FAILED
```

候选概览和正式版本分别使用：

```text
QUEUED / RUNNING / SUCCEEDED / FAILED / TIMED_OUT / CANCELLED / OBSOLETE
```

变更单使用：

```text
DRAFT / AWAITING_ACCEPTANCE / AWAITING_FUNDING / EFFECTIVE / EXECUTING /
DISPUTED / DISTRIBUTION_PENDING / SETTLED / REFUNDED / SPLIT /
CANCELLED / REJECTED
```

### 8.2 链上任务与争议状态

链上任务状态至少包含：

```text
CREATED / FUNDED / ASSIGNED / SETTLEMENT_PENDING / RELEASED /
REFUNDED / DISPUTED / DISTRIBUTION_PENDING / SPLIT / CANCELLED
```

争议登记至少包含：

```text
FROZEN / CLAIM_WINDOW / EVIDENCE_OPEN / EVIDENCE_CLOSED /
REVIEW_WINDOW / REVIEW_REQUESTED / FINALIZABLE / FINALIZED /
DISTRIBUTION_PENDING / DISTRIBUTED
```

状态要求：

- 链下可以比链上更细，但所有资金终态以链上为准。
- `FUNDED` 只表示发布者资金到账，不表示 Agent 入金。
- `canSelect`、`canAccept`、`canRequestRevision` 和 `canRequestDispute` 是后端计算能力，不是前端自行推导的状态。
- 四业务子账拥有独立并行生命周期，不得由任务主状态推断余额可用性。

## 9. 界面与交互需求

### 9.1 任务发布者端

- 登录页：模式选择、钱包连接、钱包与网络错误提示。
- 任务创建：任务规格、输入、验收标准、预算与费用拆分。
- 匹配进度：托管确认、匹配、概览生成和失败补位状态。
- 候选比较：最多 3 个概览、冻结报价、费用来源、推荐解释和可选择状态。
- 正式交付：V1–V5 时间线、父版本、差异、反馈响应、评审倒计时和当前可执行动作。
- 变更单：范围差异、责任方、资金来源、追加价格和期限。
- 资金视图：四子账、外部成本、已用/可退/不可退金额、交易确认与对账记录。
- 争议中心：资格原因、主张与反请求、冻结确认、证据目录、时间线、初裁、复核和逐账结果。

### 9.2 Agent 提供者端

- Agent 列表、创建编辑、状态、健康、容量与价格版本。
- 凭证写入/轮换与连通性测试，任何页面不得回显原凭证明文。
- 概览和正式执行队列、状态、期限、用量、版本与错误。
- 变更单、责任结论、争议案件和证据权限。
- 候选收入、正式收入、变更收入、平台费、外部成本和冲正明细。

### 9.3 通用交互规则

- “已提交”“等待链上确认”“链上已确认”必须视觉区分。
- 禁用操作必须展示后端返回的不可执行原因。
- 资金页面必须拆分展示概览费、正式本金、变更单、争议费、平台费和外部成本。
- `FormalEscrow` 全退不得描述为“全部支出退款”。
- 页面统一使用“平台争议裁决”，并展示其平台内部资金处置性质。
- 所有关键提交应防重复点击，并支持请求幂等结果恢复。

## 10. API 与数据需求

### 10.1 API 边界

- 客户端调用链固定为 `React/Vite → Next.js BFF → Go Engine`。
- BFF 负责会话接入、响应聚合与裁剪，不实现状态迁移、匹配或资金规则。
- Engine 是 RBAC、任务状态、匹配、调度、版本、成本责任和争议资格的唯一链下权威。
- 钱包交易由浏览器签名；服务端只能生成参数和监听状态。
- 关键写接口必须携带 `Idempotency-Key` 和聚合版本或 `If-Match`。

### 10.2 最小 API 能力

- 钱包 nonce、签名登录、会话与角色。
- Agent CRUD、启停、价格版本、能力、凭证轮换、健康和用量。
- 任务草稿、规格版本、验收标准、报价、发布、取消、状态与可执行动作。
- 候选概览报价、注资、生成、查询、补位与选择。
- 正式套餐、V1–V5、评审动作、修改请求、差异与交付物。
- 变更单创建、双方确认、责任、注资、执行和状态。
- 四业务子账、外部成本、平台补贴、冲正、交易和 Agent 收益。
- 争议资格、主张/反请求、和解、答辩、补证、初裁、复核、最终决定与分配。
- 管理后台的治理、死信、异常、案件分配、冲突回避与审计。

### 10.3 数据约束

- 每个任务最多一个有效 assignment。
- 当前匹配修订下，每个候选最多一个有效概览。
- 每个正式套餐最多一个活动生成，`(formal_package_id, version_no)` 唯一。
- V4/V5 必须引用有效变更单，V6 永久拒绝。
- 每个选择 nonce、work nonce、概览抵扣、变更单注资和资金消费键只能成功一次。
- 每个账务 journal 借贷平衡，原记录不可更新或删除。
- 同一案件容器允许多项主张，但同一申请人、争议类型与触发事件不得重复。
- 冻结叶子、决定指令和执行结果必须按稳定索引一一对应。

| NFR-REL-01 | SQS 至少一次投递、重复回调、事件重放和用户重复点击不得产生重复执行、版本、计费或出金。 |
| NFR-REL-02 | 链上同步必须保存交易哈希、区块、事件序号和确认状态，并处理事件乱序和链重组。 |
| NFR-REL-03 | 资金冲突以链上状态为准，长时间未确认或链上链下不一致必须告警并进入对账。 |
| NFR-REL-04 | PostgreSQL、账务、对象存储和链上事件必须具备备份、恢复、RTO/RPO 与灾难恢复演练。具体指标待阶段 0/5 冻结。 |
| NFR-REL-05 | Qdrant、Embedding、模型、Redis、RPC 和单个 Worker 故障必须有明确降级或重试路径。 |

### 11.3 性能与容量

- 候选概览必须支持最多 3 个并行 fan-out，正式版本按 assignment 严格串行。
- 容量预留必须使用带 fencing token 的租约，防止 Agent 并发超卖。
- 生产 API 延迟、任务吞吐、队列积压、最大附件、并发任务和链上确认目标值在阶段 0/5 冻结。
- 主网上线前必须完成容量压测、限流、熔断和降级验证。

### 11.4 可观测性与审计

- 日志统一关联请求 ID、任务 ID、assignment ID 和链上任务 ID。
- 监控 Agent 健康、执行成功率、延迟、超时、重试和容量。
- 监控匹配、概览、版本、变更、争议、四账余额、抵扣、退款、冲正和对账差异。
- 死信、WORM 写入失败、账本不平、冻结/退款/结算/分配失败必须告警。
- 审计记录必须覆盖高风险管理操作、权限失败、签名失败和关键状态迁移。

### 11.5 可访问性与兼容性

- Web 应支持主流桌面浏览器和响应式移动 Web。
- 核心表单、模式选择、状态提示和错误提示必须支持键盘操作与语义化辅助技术。
- 动效必须尊重系统 `prefers-reduced-motion` 设置，不得影响资金与任务操作可用性。

## 12. 技术与架构约束

| 层级 | 约束与职责 |
| --- | --- |
| `apps/web` | React/Vite 客户 UI，只负责展示与浏览器钱包交互，不直连数据库、队列或 Engine 内部接口 |
| `apps/bff` | Next.js SSR、SEO、会话接口与聚合，不实现任务状态迁移、匹配和资金规则 |
| `services/engine` | Go 领域引擎，负责 RBAC、状态机、匹配、Agent 调度、版本、计费责任和争议资格 |
| `contracts/escrow` | Solidity 资金真相源，负责托管、独立账户、退款、结算、冻结和最终分配 |
| PostgreSQL | 链下系统记录与不可变账务真相源 |
| Redis | 可重建缓存、限流、锁和协调，不保存余额真相 |
| Qdrant | 自建检索系统，不作为业务真相源；通过事务 Outbox 同步 |
| SNS/SQS/DLQ | 异步分发、至少一次消费、重试与失败隔离 |
| S3 Object Lock | 交付物、版本差异与争议证据的加密、WORM 存储 |

## 13. 验收标准

### 13.1 业务闭环验收

1. 真实 Agent 完成注册、健康检查、概览、正式交付、修改和用量上报。
2. 发布者在测试链完成四业务子账的真实入金、授权、退款、结算与对账，Agent 全程零任务级入金。
3. 平台返回最多 3 个合格、可解释候选；刷新稳定，同服务商限制和探索规则有效。
4. 候选概览按限制执行；有效概览结算、失败退款或补位正确。
5. 发布者选择授权与平台证明由合约双重校验，选择并发最多成功一次，一次抵扣与正式净额正确。
6. V1–V3 顺序执行，重试不增版；三类责任的 V4/V5 均通过变更单执行，V6 被拒绝。
7. 验收结算后，Agent 收入可立即提现或自愿生息，结算前后收益归属正确。
8. 取消、未选择、Agent 超时、平台故障、范围扩张、和解、全退和部分结算均端到端通过。
9. 发布者质量争议与 Agent 独立争议均完成资格、冻结、反请求、证据、初裁、一次复核与逐账执行。

### 13.2 安全与一致性验收

1. 重复请求、消息重放、迟到回调、事件乱序、链重组和并发点击不造成重复计费、版本或出金。
2. 四业务子账、外部成本和 Agent 收益边界正确，跨账处分、遗漏冻结叶子和双重消费全部失败。
3. 管理员不能读取凭证明文、代签用户交易、绕过状态机或直接改写资金决定。
4. 初裁与复核隔离，利益冲突账户不能接案，证据只增不改且访问留痕。
5. 每个账务 journal 借贷平衡，链上余额、金库份额、内部账本与 Agent 应收日对账一致。
6. 合约单元、属性/模糊、安全、竞态和端到端测试通过；主网前独立审计完成。

### 13.3 工程质量门禁

- `pnpm check-types`
- `pnpm test`
- `pnpm build`
- Go 单元测试与竞态检查。
- Solidity 编译、静态分析、单元和属性测试。
- API 契约、数据库迁移、Outbox、对象锁、备份恢复和灾难恢复验证。
- 任一关键门禁失败时不得合并或发布。

## 15. 待决策事项

以下项目不得由研发在实现中自行假设；必须在对应阶段开始前形成版本化决策记录。

### 15.1 阶段 0：合约、资金与治理

- 测试链、主网、托管资产和代币标准。
- 四业务子账采用单合约内独立账户还是多合约，以及 Gas 与批量结算方案。
- 概览价格上下限、正式佣金、平台费、争议/复核费、补贴与税费规则。
- 外部成本授权和不可退规则。
- 生息资产、策略、流动性缓冲、亏损顺序、风险准备金和紧急退出。
- 金额精度、比例分配舍入和尾差归属。
- 资格、初裁、复核、暂停、升级地址与多签阈值，以及 relayer 策略。
- EIP-712、证明、证据根、nonce 和跨链重放编码规范。
- Agent 控制者与收款地址的写入与轮换规则。

### 15.2 阶段 0：基础设施

- Engine/Worker 统一选择 ECS 或 EKS。
- PostgreSQL、Redis、S3、消息、账务库规格及 RTO/RPO。
- WORM 保留期、删除例外、密钥轮换和恢复流程。
- Cloudflare 源站策略、服务身份、RPC 主备和链重组策略。
- Qdrant 拓扑、Embedding 模型、向量维度、索引切换和快照解释方案。

### 15.3 阶段 1–4：执行与运营

- Agent API 认证、附件、回调和统一概览模板。
- 概览截止时间、工具白名单、用量上限和质量门槛。
- 正式交付 SLA、复杂任务评审期、21/30 日硬截止参数。
- 20% 范围阈值的分类校准、责任复核流程和平台事故补偿预算。
- 初裁/复核团队规模、专业路由、值班、回避和质量抽检。
- 交付物、证据、用量、消息和账务保存周期。
- CTR/LTR 样本量、离线指标、公平性护栏和回滚阈值。

### 15.4 阶段 5：生产与主网准入

- 合约审计与复审结果、主网多签和漏洞响应。
- 生产 SLO、容量目标、事故等级、值班和补偿标准。
- 主网白名单、单任务/用户/日限额、灰度、暂停与恢复审批。
- 用户规则、风险披露、隐私、目标市场和专项合规评估。
- 财务、税务、稳定币脱锚、Gas、批量提现和客服运营流程。
