# 《AI Engineering》内容重点整理

> 原著：Chip Huyen  
> 版本：O'Reilly 第一版（原书 2024 年 12 月首次发布）  
> 整理依据：《AI Engineering》中文本地机器翻译稿，共 385 页  
> 说明：本稿是学习型提炼，不替代原书。源 PDF 明确标注为非官方机器翻译，专业术语和细节可能存在偏差，重要内容建议对照英文原著。

## 一句话概括

AI 工程的核心不是“调用一个大模型 API”，而是围绕基础模型建立一套可评估、可适配、可优化、可监控、能从用户反馈中持续改进的完整系统。

## 30 秒掌握全书

1. **先判断问题是否值得用 AI 解决**，不要因为模型很强就强行寻找使用场景。
2. **先建立评估体系，再优化模型**。没有可靠评估，就不知道提示、RAG、微调或换模型是否真的有效。
3. 模型质量主要由三部分决定：**指令、上下文、模型本身**。
4. 按成本和复杂度逐步优化：**生成参数 → 提示工程 → RAG/工具 → 微调 → 更复杂的系统改造**。
5. RAG 主要解决“给模型正确、及时的外部知识”；微调主要改变“模型的行为、风格和任务能力”。
6. 智能体的能力来自工具、规划和记忆，但工具越多、自动化越高，故障和安全风险也越大。
7. 数据集建设关注三个指标：**质量、覆盖范围、数量**；前两者通常比盲目扩大量更重要。
8. 生产系统不能只看回答质量，还要看**延迟、吞吐、有效吞吐、成本、安全和可观测性**。
9. 每增加一个组件都同时增加能力和故障模式，因此系统应从简单架构开始，按证据演进。
10. 用户反馈是重要的数据飞轮来源，但反馈天然有偏差，使用不当会形成退化反馈回路。

## 全书主线

```text
判断是否值得构建
        ↓
理解模型能力与概率特性
        ↓
定义评估标准与评估数据
        ↓
选择模型 / API / 自托管方案
        ↓
优化指令（Prompt）
        ↓
补充上下文与工具（RAG / Agent）
        ↓
必要时修改模型（Finetuning）
        ↓
建设和验证数据集
        ↓
优化推理成本与延迟
        ↓
加入护栏、路由、缓存、监控与反馈闭环
```

作者反复强调：这是一个循环而非一次性瀑布流程。评估贯穿每一步，生产反馈又会反过来更新评估集、提示、数据和模型。

## 1. AI 工程是什么

### 核心定义

AI 工程关注如何把预训练好的基础模型适配到现实应用中。它继承了机器学习工程的系统性实验、严格评估、持续优化等原则，但工作重心发生了变化：

| 传统机器学习工程 | 基础模型时代的 AI 工程 |
|---|---|
| 收集和标注表格/任务数据 | 组织指令、上下文、偏好和反馈数据 |
| 特征工程 | 提示工程、上下文构建、工具设计 |
| 从训练模型开始 | 通常从现成模型和产品原型开始 |
| 产品开发与模型开发较分离 | AI 工程师更靠近产品和用户体验 |
| 主要优化任务指标 | 同时处理质量、安全、延迟、成本和概率性 |

### 为什么会形成一门新工程学科

- 自监督学习使模型可以利用海量无标签数据，推动语言模型扩展为大语言模型。
- 模型进一步融合图像、音频、视频等模态，成为基础模型。
- 基础模型的通用性和 API 化降低了开发门槛，使开发顺序从“先训练模型”转为“先验证产品价值”。
- 模型能力提升带来的不是应用数量线性增长，而是大量新应用模式集中涌现。

### 构建前先回答的问题

- 这个问题真的需要 AI 吗？确定性规则、搜索或普通软件是否更可靠？
- 错误的代价是什么？是否允许人类复核或降级处理？
- AI 是替代人、辅助人，还是只负责某个子步骤？
- 用户能否理解系统不稳定、可能出错的边界？
- 产品的防御性来自哪里：独有数据、用户反馈、工作流集成、品牌还是分发渠道？
- 上线后的维护、评估和监控成本是否可承担？

## 2. 理解基础模型

### 模型性能由什么决定

基础模型的表现受以下因素共同影响：

- **训练数据**：数据的语言、领域、质量和分布决定了模型擅长什么。
- **模型架构**：Transformer 依靠注意力机制并行处理上下文，但长上下文会带来计算和内存问题。
- **规模**：通常以参数量、训练 token 数和训练 FLOPs 衡量；更大不等于在每项任务上都更好。
- **后训练**：监督微调和偏好微调把预训练模型调整为更会遵循指令、更符合人类偏好的助手。
- **采样配置**：温度、Top-k、Top-p、停止条件和结构化输出约束会直接改变生成行为。

### 必须接受模型的概率性

同一输入可能产生不同输出。这种概率性使模型适合创造性任务，也导致不一致和幻觉。工程目标通常不是把 AI 变成完全确定的系统，而是通过评估、约束、检索、验证和回退机制，使整体行为足够系统化。

### 幻觉的工程含义

- 幻觉不是只靠一句“不要编造”就能完全消除的问题。
- 降低生成长度、提供可靠上下文、要求引用来源、加入事实检查和允许回答“不知道”可以缓解问题。
- 高风险任务中要验证关键事实，必要时让人类复核；不能把流畅度误认为正确性。

## 3. 评估方法论

### 为什么基础模型更难评估

- 输出开放且可有多个正确答案。
- 质量是多维的：正确、相关、完整、连贯、安全、符合风格等可能互相冲突。
- 模型与评判模型都会变化，分数不一定能跨模型、跨时间直接比较。
- 公开基准可能饱和、被训练数据污染，或与真实业务分布不一致。

### 常见评估方法

| 方法 | 适用情况 | 主要限制 |
|---|---|---|
| 功能正确性 | 代码、数学、可执行任务 | 只适用于结果可验证的任务 |
| 精确匹配 | 分类、结构化字段、固定答案 | 对表达差异过于敏感 |
| 词汇相似度 | 摘要、翻译的粗略比较 | 文字相似不代表语义正确 |
| 语义相似度 | 开放文本的近似比较 | 可能漏掉事实和细节错误 |
| AI 评判者 | 主观、多维、规模化评估 | 有偏见、不稳定、增加成本和延迟 |
| 人工评估 | 高价值、模糊或高风险问题 | 昂贵、慢、评判者间不一致 |
| 成对比较 | 很难给绝对分，但容易选优 | 只能提供相对排序，扩展成本高 |

语言模型指标（交叉熵、困惑度）可用于比较模型对文本的建模能力或发现异常数据，但不应被直接当成最终产品质量。

### AI 评判者的正确用法

- 给出明确的评分标准和正反例，而不是只问“这个回答好吗”。
- 分维度评分，避免用单一总分掩盖关键缺陷。
- 校验顺序偏差、冗长偏好、自我偏好和位置偏差。
- 用人工标注或可验证指标定期校准。
- 记录评判模型版本、提示、采样参数和评分量规。
- 不把 AI 评判者作为唯一证据，尤其是高风险任务。

## 4. 建立评估驱动的开发流程

### 评估标准应贴近业务

通用指标不足以决定模型是否适合具体应用。实际需要综合：

- 领域能力和任务正确性；
- 生成质量：流畅、连贯、相关、忠实；
- 事实一致性与幻觉率；
- 安全、隐私、偏见和合规；
- 指令遵循和角色一致性；
- 延迟、成本、稳定性和可用性。

评估指标应与业务指标建立联系。例如客服系统不应只看“回答看起来不错”，还应看一次解决率、转人工率、投诉率、处理时长和用户留存。

### 推荐的评估流水线

1. **拆解系统**：既评估端到端结果，也评估检索器、模型、工具调用、护栏等组件。
2. **定义标准**：为每个标准给出可操作定义、评分范围和边界条件。
3. **编写评分量规**：提供好、坏和临界样例，减少评判歧义。
4. **建立评估集**：覆盖常见请求、长尾、对抗输入和历史事故。
5. **组合评估方式**：尽量采用确定性检查，再补充 AI 评判和人工审核。
6. **设定发布门槛**：明确哪些指标下降会阻止上线。
7. **持续迭代**：把生产失败样本加入回归集，并对评估资产做版本控制。

### 模型选择：API 还是自托管

要从以下维度权衡，而不是只看排行榜：

- 数据隐私与合规；
- 模型和训练数据的血缘、版权与许可；
- 自有评估集上的性能；
- 上下文长度、结构化输出、工具调用、多模态等功能；
- API 费用与内部工程、硬件、运维成本；
- 控制权、可审计性、版本稳定性和供应商锁定；
- 是否需要端侧部署或离线运行。

公开基准适合快速淘汰明显不合格的模型，但最终选择应依靠私有评估集。

## 5. 提示工程

### 提示的作用

提示工程是用指令和示例让模型表现出目标行为。它门槛低，但做好并不容易；模型对措辞、上下文顺序、模板和示例可能非常敏感。

### 实用原则

- 明确说明任务、目标读者、成功标准和禁止事项。
- 提供足够但相关的上下文，避免把上下文窗口当作垃圾场。
- 给出高质量示例，尤其是边界案例和期望格式。
- 用结构化输出约束字段、类型和格式。
- 将复杂任务拆成可验证的子任务。
- 需要推理时给模型更多测试时计算，但要评估它带来的成本和延迟。
- 对提示进行实验、版本控制、回归测试和变更记录。
- 确保线上聊天模板与模型训练时的格式一致。

### 提示安全

主要风险包括越狱、直接提示注入、网页或文档中的间接提示注入、系统提示泄漏和敏感信息抽取。

防御需要多层配合：

- **模型层**：选择安全性更好的模型，必要时进行安全对齐。
- **提示层**：区分指令与不可信数据，明确权限和拒绝规则。
- **系统层**：最小权限、工具参数校验、输入/输出过滤、速率限制、异常检测、人工审批和审计。

任何单层防御都不可靠。尤其不能让模型仅凭自然语言自行决定是否执行高影响操作。

## 6. RAG 与智能体

### RAG 的本质

RAG 先从外部数据源检索相关信息，再把信息提供给模型生成回答。它可以补充新知识、私有知识和超出上下文窗口的知识，并降低每次都输入全部资料的成本。

### RAG 成败首先取决于检索

- 基于关键词的稀疏检索（如 BM25）简单、便宜、适合精确术语，应作为强基线。
- 基于嵌入的密集检索擅长语义相似，但计算成本更高，也可能漏掉精确关键词。
- 混合检索通常比押注单一路线更稳健。
- 分块策略、查询重写、元数据过滤、重排序和上下文压缩都会显著影响最终效果。
- 检索评估和生成评估要分开，否则难以判断错误来自“没找到”还是“找到但没用好”。

### 智能体的组成

智能体通常由以下部分构成：

- **环境**：智能体可以观察和影响的范围；
- **工具**：搜索、数据库、代码、API 或写操作；
- **规划**：拆解任务、选择步骤和工具；
- **执行与反思**：检查结果，发现错误后调整计划；
- **记忆**：保存必要状态、历史信息和经验。

### 智能体的主要失败模式

- 计划错误或过度规划；
- 选错工具、参数错误、工具本身失败；
- 中间错误逐步放大；
- 陷入循环，成本和延迟失控；
- 记忆过期、矛盾或污染；
- 工具权限过大导致安全事故。

工程上应限制最大步数、最大成本和可用工具；对写操作使用最小权限、幂等设计、确认机制与可追踪日志。

## 7. 微调

### 什么时候考虑微调

适合微调的情况：

- 需要稳定改变模型的行为、风格或输出格式；
- 任务模式可从高质量示例中学习；
- 提示太长，导致持续的 token 成本和延迟；
- 提示与 RAG 已达到瓶颈，且评估证明微调可能带来增益；
- 有足够高质量、合法且覆盖真实分布的数据。

不宜急于微调的情况：

- 问题主要是知识缺失、知识更新或引用来源，此时优先 RAG；
- 没有可靠评估集，无法证明效果；
- 数据量小、质量差或不具代表性；
- 强模型加少量提示已经满足需求；
- 团队无法承担训练、部署、回归测试和后续维护。

### RAG 与微调的区别

| 需求 | 优先考虑 |
|---|---|
| 注入最新或私有事实 | RAG |
| 回答需要给出可追溯来源 | RAG |
| 改变语气、格式、决策习惯 | 微调 |
| 学习稳定的领域任务模式 | 微调 |
| 同时需要知识和行为适配 | RAG + 微调 |

### 参数高效微调

完整微调需要为大量参数保存权重、梯度和优化器状态，内存成本很高。PEFT 只训练少量参数；LoRA 用低秩矩阵表示权重更新，是最常用方案之一。量化与 LoRA 结合可进一步减少显存需求。

微调成功仍取决于数据、基础模型选择和超参数。应重点监控学习率、批大小、训练轮数、训练/验证损失和提示损失权重，警惕过拟合与能力退化。

## 8. 数据集工程

### 三个核心标准

1. **质量**：数据是否正确、相关、一致、合规，标注是否能真实体现目标行为。
2. **覆盖范围**：是否包含常见场景、长尾、不同用户群体、边界条件和失败案例。
3. **数量**：在质量与覆盖足够后，更多数据才更可能带来稳定收益。

“少量高质量、多样的数据可能优于大量噪声数据”是本章最重要的判断之一。

### 数据流程

- 从模型应学会的行为出发设计数据，而不是先收集一堆数据再找用途。
- 记录数据来源、许可、处理步骤、标注者和版本，保证数据血缘可追踪。
- 检查、去重、清洗、过滤和格式化；训练与推理格式要一致。
- 对标注指南做版本控制，并评估标注者间一致性。
- 将生产中的失败和人工修正沉淀为高价值样本。

### 合成数据

合成数据适合扩大稀缺场景、生成指令数据、覆盖边界条件和做模型蒸馏，但必须验证：

- 是否只是表面模仿而没有真实能力；
- 是否继承或放大生成模型的错误和偏见；
- 是否与真实数据重复或泄露测试集；
- 是否因反复使用模型生成内容造成分布退化或模型坍塌；
- 数据来源、许可和生成过程是否可追踪。

生成数据容易，自动判断什么数据值得生成、制定高质量标注标准和可靠验证更难。

## 9. 推理优化

### 先定义指标

- **端到端延迟**：从请求到完整响应的时间。
- **首 token 时间（TTFT）**：主要受预填充阶段影响，决定用户多久看到响应开始。
- **每 token 时间（TPOT）**：主要受解码阶段影响，决定流式输出速度。
- **吞吐量**：单位时间处理的请求或 token 数。
- **有效吞吐量（goodput）**：满足服务等级目标的有效请求量。
- **利用率**：硬件计算和内存能力被使用的程度。

延迟与吞吐通常存在权衡：更积极的批处理能降低单位成本、提高吞吐，却可能增加单请求等待时间。

### 优化分两层

**模型层优化**可能改变模型行为，因此需要重新做质量评估：

- 量化；
- 蒸馏和模型压缩；
- 推测解码、并行解码；
- KV cache 和注意力机制优化；
- 针对硬件的内核与编译优化。

**服务层优化**主要改变服务方式：

- 动态/连续批处理；
- 预填充与解码解耦；
- 提示缓存；
- 张量、流水线、副本等并行策略；
- 在线请求与批量请求分流。

选择技术必须依据真实工作负载。长上下文场景更关注 KV cache；共享长系统提示或多轮对话更适合提示缓存；低延迟优先时可能增加副本；成本优先时可接受更强批处理。

## 10. 生产架构、可观测性与用户反馈

### 推荐的渐进式架构

书中建议按需求逐步加入以下能力：

1. **增强上下文**：RAG、会话状态、用户信息和工具结果。
2. **设置护栏**：输入检测、输出检查、权限限制和敏感信息保护。
3. **添加模型路由与网关**：统一鉴权、限流、重试、版本、成本统计，并按任务路由模型。
4. **加入缓存**：精确缓存适合完全重复请求，语义缓存可复用相似请求但存在误命中风险。
5. **加入智能体模式**：只在任务确实需要多步规划和工具操作时增加复杂度。

组件要保持模块化，但边界可以按系统需求落地。每增加一个组件都要同步增加评估、监控和故障处理。

### 监控与可观测性

- **监控**告诉你已知指标是否异常。
- **可观测性**帮助你从指标、日志和调用链追踪中理解未知故障为何发生。

除常规系统指标外，还应追踪：

- 模型、提示、检索索引和工具版本；
- token 数、TTFT、TPOT、成本和缓存命中率；
- 检索结果、工具调用、智能体步骤和终止原因；
- 拒答、护栏触发、解析失败和回退率；
- 质量代理指标、用户修正、投诉和转人工率；
- 输入分布、输出分布与用户行为漂移。

日志必须保护隐私和秘密，不能默认记录完整敏感提示、个人信息或凭证。

### 用户反馈

除了点赞/点踩，还可以从行为中提取反馈：重新生成、提前终止、修改答案、继续追问、转人工、投诉、会话长度和任务是否完成。

反馈设计应注意：

- 只在用户有足够信息、且反馈成本较低时提问；
- 明确询问具体维度，模糊的总评分信息量有限；
- 反馈者不是所有用户的随机样本，存在选择偏差、位置偏差和近期偏差；
- 用户通常只能评价自己看到的答案，未曝光内容没有反馈；
- 直接用反馈训练模型可能让系统变得迎合用户而不是更准确。

### 退化反馈回路

当模型输出影响用户反馈，而反馈又决定下一版模型时，早期微小偏差会被持续放大。例如推荐系统让排名靠前的内容获得更多点击，点击又进一步提高排名。应通过探索流量、随机对照、分群分析、人工审计和离线评估避免把“曝光更多”误判为“质量更高”。

## 最重要的决策框架

### 遇到质量问题时，按什么顺序排查

1. 问题和成功标准是否定义清楚？
2. 评估集是否覆盖真实用户和失败场景？
3. 采样参数、输出约束和提示模板是否正确？
4. 指令是否清晰，示例和上下文是否相关？
5. 检索是否找到了正确资料，重排序是否合理？
6. 模型是否适合该语言、领域和任务？
7. 是否需要微调来改变稳定行为？
8. 是否需要改变整体工作流，引入验证、人工复核或任务拆解？

### 何时从简单方案升级

| 当前方案 | 只有在出现以下证据时再升级 |
|---|---|
| 单次模型调用 | 评估显示缺少知识、步骤或验证能力 |
| 更好的提示 | 提示无法稳定注入所需知识或行为 |
| RAG | 检索质量已较好，但模型仍不会按目标方式完成任务 |
| 单智能体 | 任务天然需要明确的并行角色或隔离权限 |
| 模型 API | 数据、成本、延迟、控制或可用性要求无法满足 |
| 通用模型 | 私有评估证明领域模型或微调有稳定、可复现收益 |

## 可直接使用的项目清单

### 产品与风险

- [ ] 问题必须使用 AI 才能带来明显价值。
- [ ] 已定义 AI、人类和确定性程序各自负责的部分。
- [ ] 已明确不可接受的错误及其业务影响。
- [ ] 高风险操作需要确认、审批或人工复核。
- [ ] 产品向用户清楚表达能力边界和不确定性。

### 评估

- [ ] 评估标准与业务目标相连。
- [ ] 有代表常见、长尾、对抗和历史事故的评估集。
- [ ] 组件级评估与端到端评估同时存在。
- [ ] 优先使用可执行、可验证的确定性指标。
- [ ] AI 评判者已用人工数据校准并测试偏差。
- [ ] 模型、提示、采样、数据和评估配置均有版本记录。
- [ ] 发布流程包含明确的质量和安全门槛。

### RAG 与智能体

- [ ] 关键词检索已作为基线并与向量检索比较。
- [ ] 已单独衡量检索召回、排序和最终生成质量。
- [ ] 检索内容被视为不可信数据，不能覆盖系统指令。
- [ ] 工具遵循最小权限原则，输入参数经过验证。
- [ ] 写操作具备幂等、确认、审计和失败恢复机制。
- [ ] 智能体设置最大步骤、成本、时间和循环检测。

### 数据与微调

- [ ] 已证明问题不能只通过提示、检索或换模型解决。
- [ ] 训练数据质量、覆盖和许可均可验证。
- [ ] 训练集、验证集、测试集和生产样本之间无泄漏。
- [ ] 训练格式与推理格式一致。
- [ ] 微调后重新评估通用能力、安全、延迟和成本。
- [ ] 合成数据经过独立验证，并记录生成模型与参数。

### 生产运行

- [ ] 跟踪端到端延迟、TTFT、TPOT、吞吐和有效吞吐。
- [ ] 跟踪 token、缓存、模型路由和单请求成本。
- [ ] 可以追踪一次请求经过的检索、模型和工具步骤。
- [ ] 敏感数据、密钥和个人信息不会进入普通日志。
- [ ] 有超时、重试、熔断、降级和人工接管方案。
- [ ] 生产失败会进入评估回归集。
- [ ] 用户反馈已做偏差分析，并防范退化反馈回路。

## 常见误区

- **“模型更大就一定更适合。”** 实际应看目标任务、语言、延迟、成本、功能和私有评估结果。
- **“公开排行榜第一就是最佳选择。”** 排行榜数据可能被污染，且通常不代表业务分布。
- **“RAG 可以消除幻觉。”** RAG 还可能检索错误、遗漏关键内容或被模型误用。
- **“微调可以给模型注入最新知识。”** 需要更新、引用和删除的知识通常更适合外部检索。
- **“提示工程只是写一句聪明的话。”** 生产提示需要版本控制、评估、模板管理和安全设计。
- **“AI 评判者给了高分，所以系统可靠。”** 评判模型同样有偏见、漂移和不一致。
- **“用户点赞越多，模型越好。”** 曝光、界面、用户群和选择偏差都可能制造虚假信号。
- **“多加组件就会更强。”** 组件同时增加延迟、成本和故障面，应由评估证据驱动。
- **“上线后只监控服务器指标即可。”** AI 故障常发生在质量、检索、工具调用、安全和数据漂移层面。

## 术语速查

| 术语 | 简明解释 |
|---|---|
| Foundation Model | 在大规模通用数据上预训练、可适配多个下游任务的模型 |
| Post-training | 预训练后进行的监督微调、偏好对齐等过程 |
| Sampling | 根据 token 概率分布选择下一个 token 的生成过程 |
| Hallucination | 模型生成看似合理但不受事实或上下文支持的内容 |
| Eval | 用数据、标准和方法系统衡量模型或应用表现 |
| AI-as-a-Judge | 使用另一个 AI 模型评价输出质量 |
| RAG | 先检索外部信息，再让模型基于该信息生成 |
| Agent | 能观察环境、规划步骤并调用工具执行任务的系统 |
| PEFT | 只训练少量参数以降低微调资源消耗的方法集合 |
| LoRA | 用低秩矩阵表示权重更新的参数高效微调方法 |
| Quantization | 用更少位数表示权重或激活，以降低内存和计算成本 |
| TTFT | 从请求发出到生成第一个 token 的时间 |
| TPOT | 解码阶段生成每个输出 token 的平均时间 |
| Goodput | 在延迟等服务约束内真正有效完成的吞吐量 |
| KV Cache | Transformer 推理中缓存注意力键和值，减少重复计算 |
| Guardrail | 对输入、输出、权限和行为进行约束与检测的安全机制 |
| Model Gateway | 统一管理模型访问、鉴权、限流、路由、观测和成本的入口 |
| Data Flywheel | 利用产品使用和反馈持续生成数据、改进系统的闭环 |

## 最终结论

这本书真正想建立的是一种工程判断力：

> 从明确问题和评估开始，用最简单的方案验证价值；再根据证据逐步加入上下文、工具、微调和系统组件；最后依靠可观测性与用户反馈持续改进，同时始终控制安全、成本和复杂度。

决定一个 AI 应用能否长期工作的，通常不是某一次模型调用的惊艳程度，而是团队能否把模型的不确定性纳入一个可测量、可约束、可恢复、可迭代的系统。
